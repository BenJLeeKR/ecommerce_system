# Orchestrator Runtime DB 운영 기준

본 문서는 Thin Orchestrator Runtime의 상태 및 기록 관리를 담당하는 SQLite DB의 운영 및 관리 기준을 정의한다.

## 1. 개요 및 목적

Orchestrator는 상태, 컨텍스트, 작업 기록을 유지하기 위해 SQLite DB를 사용한다. 시스템의 연속성, 백업/복구, 보안을 위해 이 DB 파일은 Git 작업 트리가 아닌 독립된 외부에 저장되어야 한다.

## 2. 외부 저장 원칙 및 경로

- **현재 상태**: SQLite DB 경로는 코드 내에 고정되지 않고, 명시적인 호출자(Caller) 주입(Injection) 방식을 유지한다. 현재 `ORCHESTRATOR_JULES_STATE_DIR` 환경 변수를 이용한 검증과 **Jules 전용 상태 저장소 팩토리(`get_jules_state_repository`) 및 테스트 연결 준비가 완료**되었다. 단, 실제 코드 호출부에서 repository를 생성·주입하거나 운영 환경용 Runtime DB를 실제로 초기화하는 작업은 포함되지 않았으며, 이는 사용자 승인 후 후속 작업으로 진행된다. (경로는 반드시 절대 경로 및 Git 작업 트리 외부여야 함)
- **목표 상태 (이관 대상)**: 운영 환경에서의 안정성을 위해 최종적으로 `/workspace/runtime/` 경로로 설정할 예정이다. 향후 별도의 승인과 작업을 거쳐 기존 호출부를 연결하고 실제 `.env` 및 디렉터리/DB 환경을 구성하게 된다.
- **Git 통제**: 상태 디렉터리와 내부 DB 파일은 절대 Git 리포지토리에 커밋되지 않아야 하며, Git 작업 트리 외부에 존재해야 한다.

## 3. 접근 권한 기준

- DB 파일 및 저장 디렉터리는 최소 권한 원칙을 준수하여 구성해야 한다.
- 향후 이관될 `/workspace/runtime/` 디렉터리 및 내부의 SQLite DB 파일은 지정된 실행 계정만이 읽기 및 쓰기 권한을 가지도록 제한한다.

## 4. 백업 및 복구 기준

시스템 장애나 데이터 손실 시 Orchestrator 상태 복구를 위해 정기적인 백업 체계가 마련되어야 한다.

- 백업 대상: Runtime DB가 저장되는 주입 경로 또는 목표 경로의 전체 파일.
- RPO (Recovery Point Objective) 및 RTO (Recovery Time Objective): 기준 설정 필요.
- 백업 주기 및 보존 기간: 시스템 운영 요구사항에 맞춰 정의 필요.

## 5. 보안 및 기록 제한

다음의 정보들은 DB 내용이나 운영 과정에서 발생하더라도 어떠한 경우에도 파일, Git 커밋, PR, 문서, Worklog에 기록되어서는 안 된다:
- API 키, 인증 토큰
- Source Resource Name
- 원시 프롬프트 내용
- 원시 활동 로그, 원시 시스템 로그
- SQLite DB 파일 그 자체 및 덤프 내용

## 6. 미결 결정 사항 (사용자 확인 필요)

본 문서에서 정의된 원칙을 실제 환경에 적용하기 위해서는 다음 사항들에 대한 사용자의 명시적 결정과 백로그 등록이 필요하다:
- **실행 계정**: DB 파일의 소유권 및 권한을 부여할 구체적 시스템 계정 이름.
- **실제 이관 시점**: 호출자 주입 방식에서 `/workspace/runtime/` 경로로의 전환(이관) 시기.
- **백업 정책 세부사항**: 백업 실행 주기, 데이터 보존 기간.
- **복구 목표**: RPO 및 RTO 시간 목표.

해당 결정 사항들은 Backlog 항목으로 관리된다.
