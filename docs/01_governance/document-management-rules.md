# 문서 관리 규칙

> 상태: Draft — 프로젝트 문서 구조를 일관되게 관리하기 위한 기준이다.
> 적용 범위: `docs/` 하위의 프로젝트 문서. 외부 참고 자료의 원문 자체에는 적용하지 않는다.

## 1. 목적

- 현재 유효한 기준 문서와 작업 과정 기록을 분리한다.
- 문서의 생성·검토·승인·대체 이력을 추적 가능하게 유지한다.
- 문서가 늘어나도 팀원이 필요한 정보를 빠르게 찾을 수 있게 한다.

## 2. 문서 경로와 역할

| 경로 | 역할 |
|---|---|
| `docs/00_project/` | 프로젝트 범위, 목표, 기술 스택 등 최상위 결정 |
| `docs/01_governance/` | 작업·품질·배포·문서 관리 규칙과 역할 정의 |
| `docs/02_design/` | 승인된 아키텍처·도메인·API·DB·화면 설계 기준 |
| `docs/03_planning/` | 큰 작업의 범위, 단계, 검증, 롤백 계획 |
| `docs/04_analysis/` | 조사, 원인 분석, 대안 비교 및 판단 근거 |
| `docs/05_worklog/` | 실제 수행 작업, 결정, 검증 결과의 기록 |
| `docs/06_backlog/` | 아직 시작하지 않은 작업 후보와 우선순위 |
| `docs/07_templates/` | 문서 유형별 표준 양식 |
| `docs/08_archive/` | 더는 기준으로 사용하지 않는 대체·폐기 문서 |
| `docs/99_reference/` | 프로젝트 범위를 대체하지 않는 외부·참고 자료 |

`docs/README.md`는 전체 문서 지도로 사용한다. 각 번호 경로의 `README.md`는 해당 경로의 인덱스만 담당한다.

## 3. 인덱스 작성 원칙

- `README.md`에는 문서마다 한두 줄의 짧은 설명과 링크만 남긴다.
- 판단 근거, 상세 작업 내용, 검증 결과는 반드시 개별 문서에 기록한다.
- 인덱스에서 동일한 내용을 길게 반복하지 않는다.
- 새 문서를 만들거나 상태를 변경하면 해당 경로의 인덱스도 같은 변경에서 갱신한다.

## 4. 식별자와 파일명

| 유형 | 식별자 | 파일명 형식 |
|---|---|---|
| Worklog | `WL` | `WL-0001-YYYY-MM-DD-작업-요약.md` |
| Backlog | `BL` | `BL-0001-작업-요약.md` |
| Analysis | `AN` | `AN-0001-YYYY-MM-DD-주제.md` |
| Planning | `PL` | `PL-0001-YYYY-MM-DD-작업-요약.md` |
| Design Decision | `DS` | `DS-0001-결정-요약.md` |

- 번호는 문서 유형별로 순차 증가시키며, 삭제된 번호는 재사용하지 않는다.
- 파일명 요약은 소문자 영문과 하이픈을 사용한다.
- 기존 기준 설계 문서는 안정적인 의미 기반 파일명을 유지할 수 있다.

## 5. 문서 상태

| 상태 | 의미 |
|---|---|
| `Draft` | 작성 또는 검토 중이며 기준으로 확정되지 않음 |
| `In Review` | 승인자 검토를 요청한 상태 |
| `Approved` | 승인되어 현재 기준으로 사용 가능 |
| `Completed` | 작업 기록 또는 분석이 완료된 상태 |
| `Superseded` | 새 문서로 대체되었으며 더는 기준이 아님 |
| `Archived` | 보관 전용이며 현재 작업의 기준이 아님 |

설계 문서의 상태를 변경하거나 대체할 때는 연결된 Worklog에 이유와 영향 범위를 남긴다.

## 6. 문서 간 연결

- 시작하지 않은 작업은 Backlog(`BL`)에 기록한다.
- 조사 또는 대안 비교가 필요하면 Analysis(`AN`)를 작성하고 Backlog 항목을 연결한다.
- 여러 단계·위험 영역·롤백 검토가 필요한 작업은 Planning(`PL`)을 작성하고 승인 후 진행한다.
- 실제 수행 내용과 검증 결과는 Worklog(`WL`)에 기록한다.
- 현재 유효한 정책·구조·계약은 Design 또는 Governance 기준 문서에 반영한다.

문서 본문 상단에는 가능한 범위에서 연결된 `BL`·`AN`·`PL`·`WL` 식별자와 관련 기준 문서를 명시한다.

## 7. 변경·보관 원칙

- 기준 설계를 변경하면 Worklog만 남기지 않고 해당 기준 설계 문서를 함께 갱신한다.
- 기존 문서를 대체할 때는 새 기준 문서와 대체 사유를 명시한 뒤 기존 문서를 `Superseded` 또는 `Archived`로 표시한다.
- 중복 문서는 즉시 삭제하지 않는다. 활성 문서와의 차이, 참조 여부, 보관 필요성을 먼저 확인한다.
- 파일이나 경로를 이동할 때는 문서 내 링크와 `CLAUDE.md`의 참조를 함께 갱신하고 링크 검증을 수행한다.
- `docs/99_reference/` 문서는 승인된 요구사항과 설계 기준을 대체하지 않는다.

## 8. 작업 단위와 검증

- 문서 체계 변경도 별도 이슈와 PR 단위로 관리한다.
- 하나의 PR에는 가능한 한 한 가지 정리 목적만 담는다.
- 문서 변경 후에는 최소한 다음을 확인한다.
  1. 새 파일이 올바른 경로와 파일명 규칙을 따르는지
  2. 인덱스 링크가 실제 파일을 가리키는지
  3. 이동·삭제가 있다면 기존 참조가 깨지지 않는지
  4. `git diff --check`가 통과하는지

## 9. 적용 순서

이 규칙을 기준으로 다음 순서로 문서 체계를 정리한다.

1. Worklog·Backlog·Analysis·Planning 경로와 템플릿을 추가한다.
2. 최초 Backlog와 Worklog를 등록한다.
3. 기존 문서의 잘못된 링크와 중복 archive를 정리한다.
4. 기존 설계·거버넌스·참고 문서를 목표 경로로 단계적으로 이동한다.
5. 전체 문서 지도(`docs/README.md`)를 완성하고 최종 링크 검증을 수행한다.
