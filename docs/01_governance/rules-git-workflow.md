# Git / 브랜치 / 커밋 / PR 규칙

> 이 문서는 실제 커밋·브랜치·PR·릴리스 태그 작업을 할 때 참조한다.

## 브랜치 전략

- `main` — 사용자 승인으로 병합된 통합·릴리스 후보 기준 브랜치
- `feature/이슈번호-설명` — Jules 또는 Claude Code가 작업하는 기능·문서 변경 브랜치
- `hotfix/설명` — 승인된 릴리스의 긴급 수정 브랜치

현재는 별도 `develop` 브랜치를 사용하지 않는다. 향후 병렬 통합이 필요해 재도입하려면 테스트·릴리스 흐름을 별도 분석·승인한다.

`main` 직접 커밋과 자동 병합은 금지한다. 모든 변경은 PR로 제안하고, Codex 검토와 사용자의 명시적 병합 승인을 거쳐 반영한다.

## 실행 에이전트와 브랜치

- 작업 지시와 PR 설명에 실행 에이전트(Jules 또는 Claude Code)를 기록한다.
- 하나의 브랜치·PR은 하나의 실행 에이전트만 수정한다. 다른 에이전트의 수정이 필요하면 Codex가 수정 프롬프트를 작성해 같은 담당 에이전트에 전달하거나, 새 작업으로 분리한다.
- Jules는 GitHub 브랜치·PR까지만 작업하며, 병합 후 개발·테스트 경로 동기화는 Codex 또는 승인된 배포 절차가 수행한다.

## 커밋 메시지

- 이슈 번호를 포함한다. 예: `[#12] 장바구니 수량 변경 API 추가`
- 하나의 커밋은 하나의 논리적 변경 단위로 유지한다.

## PR 규칙

- 이슈 1개당 PR 1개
- PR 설명에는 최소한 다음을 포함한다.
  - 관련 이슈 번호와 실행 에이전트
  - 변경 파일 목록 및 변경 이유
  - 테스트 방법 및 결과
  - 스크린샷/재현 절차 (UI 변경 시)
  - 롤백 방법
- 테스트 실패, Codex 검토 미완료, 사용자 병합 미승인 상태에서는 병합하지 않는다.
- 변경 파일 10개 이내 / diff 400줄 이내를 넘으면 분할을 우선 검토한다.

## 릴리스 태그

- 테스트계 검증과 사용자의 운영 승격 승인을 마친 `main` 커밋에만 릴리스 태그를 생성한다.
- 태그는 `vMAJOR.MINOR.PATCH` 형식을 사용한다. 예: `v0.1.0`, `v0.1.1`, `v0.2.0`.
- 운영 배포 후 태그를 이동·재사용하지 않는다. GitHub 태그 보호 규칙의 실제 설정은 별도 작업으로 관리한다.
- 태그 생성 시 대상 커밋 SHA, 테스트계 검증 결과, 배포 이미지 digest, 롤백 대상 이전 태그를 릴리스 기록에 남긴다.
