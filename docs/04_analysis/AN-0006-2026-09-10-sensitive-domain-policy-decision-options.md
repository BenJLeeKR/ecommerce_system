## 1. 분석 목적과 질문
본 분석 문서는 `PL-0008`에서 유예된 항목인 '민감 영역 선결 조건'에 대한 구체적인 분석 및 대안을 제시하여 사용자(기획/설계 의사결정권자)의 최종 승인을 받기 위함입니다.
분석 대상 질문은 다음과 같습니다:
1. 고객 경험과 점유율 간 최적의 재고 예약 유효시간(TTL)은 얼마인가?
2. PostgreSQL 환경 내에서 다중 주문·결제 트래픽에 대응할 최적의 재고 동시성 및 트랜잭션 제어 방식은 무엇인가?
3. 외부 PG 시스템과 통신할 때 중복 및 지연 발생 시 시스템 멱등성 및 정합성을 어떻게 유지할 것인가?
4. 프로젝트 전용 DB에서의 백업 및 복구 인프라 전략은 담당자에게 어떻게 확인해야 하는가?

**주의:** 이 문서에 제시된 방안은 모두 "Codex 권장안"이며, 승인 시까지는 대기 상태입니다. 정책 반영은 사용자 승인 후 별도의 설계/구현 PR에서 진행됩니다.

## 2. 범위와 전제
- **포함 범위**: 재고 예약 TTL, 재고 동시성 및 트랜잭션 범위, PG 멱등성 보장 및 실패/콜백 정책, 인프라 백업/복구 체크리스트.
- **기본 전제**:
  - 신규 인프라(Redis, Kafka 등) 도입 없이 현재 아키텍처(PostgreSQL, 단일 프로젝트 전용 DB, 최소 권한 계정 분리) 내에서 해결.
  - 시간대(KST) 및 저장 기준(UTC) 원칙 준수.
  - 기존 설계 문서 및 정책(A안, 복수형 테이블명 사용, 리뷰 도메인 MVP 제외 등)은 재논의하지 않음.

## 3. 조사 결과와 근거 및 대안 비교

### 3.1. 재고 예약 TTL
결제 진행 중 오버셀링을 막기 위한 재고의 임시 점유(예약) 시간에 대한 정책입니다.

| 대안 | 장점 | 단점 | 판단 (Codex 권장안) |
|---|---|---|---|
| **10분** | 장기 점유에 따른 판매 기회 손실 최소화 | 결제가 조금이라도 지연될 경우 예약 만료로 주문 실패 위험 증가 | |
| **15분** | 결제 앱 연동, 카드사 인증 등 통상적인 결제 지연을 충분히 수용하면서 판매 기회 손실 균형 유지 | 짧은 TTL(10분)보다는 약간의 판매 기회 지연 발생 | **권장** |
| **20분 이상** | 결제 지연이나 이탈 시 고객이 다시 돌아올 시간적 여유 제공 | 잦은 단순 변심 시 실제 구매자의 상품 구매 제한 발생 위험 | |

- **영향 및 근거**: 15분은 통상적인 이커머스 PG 인증 시 발생할 수 있는 지연 시간을 방어하기 충분한 시간입니다.
- **예약 만료 처리**: 주문은 스케줄러를 통해 KST 기준으로 상태 전환 판단을 하되, 만료 시점 값 자체는 UTC로 DB에 저장하여 글로벌 표준에 부합하게 합니다. (스케줄러 실행 주기는 아래 표의 사용자 결정 대기 항목으로 추가 제안합니다.)

### 3.2. 재고 동시성 제어 및 트랜잭션 경계
분산 락(Redis 등)을 도입하지 않으므로 PostgreSQL 내부의 기능으로 해결해야 합니다.
주문 생성과 재고 예약을 묶는 트랜잭션과 PG 결제와 재고 확정을 묶는 트랜잭션 경계를 설정합니다.

| 대안 | 장점 | 단점 | 판단 (Codex 권장안) |
|---|---|---|---|
| **조건부 원자 갱신 (Optimistic-like)** <br>`UPDATE inventory SET quantity = quantity - X WHERE quantity >= X` | DB 락 점유 시간이 매우 짧아 동시 처리 성능 우수, 데드락 위험 낮음 | 업데이트 실패 시 어플리케이션 레벨의 재시도 또는 실패 처리 로직 구현 필요 | **권장** |
| **비관적 락 (SELECT ... FOR UPDATE)** | 트랜잭션 단위로 강한 일관성 보장, 앱 로직이 단순함 | 트랜잭션 대기로 인해 성능 저하 가능성, 다중 테이블 접근 시 데드락 위험 | |
| **높은 격리 수준 (Serializable)** | 완벽한 정합성 보장 | 성능 저하가 극심하며, 트랜잭션 실패(재시도)율이 매우 높음 | |

- **영향 및 근거**: 모놀리스 환경이고 트래픽 급증을 대비하여 조건부 원자 갱신이 성능면에서 우월하며 단일 DB에 부하를 덜 줍니다.
- **트랜잭션 경계**:
  1. [주문 생성 + 재고 예약 (조건부 갱신)] -> 1개의 트랜잭션
  2. [PG 호출 (트랜잭션 밖)]
  3. [PG 결과 콜백 처리 + 결제 상태 갱신 + 재고 차감 확정] -> 1개의 트랜잭션

### 3.3. 결제 PG 멱등성 및 실패 정책
네트워크 단절, 타임아웃, 중복 콜백 발생 시 데이터 정합성을 유지하기 위한 정책입니다.

| 대안 | 장점 | 단점 | 판단 (Codex 권장안) |
|---|---|---|---|
| **복합 멱등성 처리**<br>- 결제 시도마다 고유한 멱등키(예: 주문 ID + 시도 순번)<br>- 결제 상태 `REQUESTED` 시에만 콜백 갱신 허용 | 중복 결제 승인 원천 차단, 지연 콜백으로 인한 과거 상태 덮어쓰기 방지 | 구현 복잡도 증가, 모든 상태 전이에 대한 명시적 조건(WHERE) 처리 필요 | **권장** |
| **단순 콜백 덮어쓰기** | 구현이 매우 단순 | 중복 콜백이나 순서가 뒤바뀐 콜백(예: 취소 후 성공 도착)으로 인한 치명적 오류 발생 가능성 | |

- **영향 및 근거**: 결제는 금전과 직결되므로 안전장치를 3중으로 두는 것이 필수적입니다.
- **처리 선택지**:
  - **중복 콜백**: 정상적인 중복 호출은 `idempotency_key` 및 멱등 처리 로직에 의해 무시되나, 이미 `FAILED` 또는 `CANCELED` 처리된 후 도착한 '지연·역순(성공) 콜백' 등 상태 전이와 불일치하는 예외 시나리오는 단순 무시하지 않고 별도의 모니터링 로그 기록 후 PG 거래 조회 및 운영팀 수동 확인(대사 작업) 절차로 연계하는 것을 권장합니다.
  - **타임아웃/반복 실패 정책 및 횟수**: 무한 재시도를 방지하기 위한 실패 누적 횟수 제한(예: 3회) 및 재고 복구 방안을 아래 사용자 결정 표로 도출합니다.

### 3.4. 인프라 확인 (체크리스트)
공용 PostgreSQL 기반 전용 DB 구성이 승인되었으므로, 실제 인프라 담당자에게 확인해야 할 백업/복구 운영 체크리스트입니다.

| 확인 항목 | 담당자 확인 필요 내용 (체크리스트) | 목적 | 판단 (Codex 권장안) |
|---|---|---|---|
| **백업 주기 및 보존** | - 전체 백업(Full) 및 증분(Incremental) 주기<br>- 백업 파일 보존 기간<br>- 저장 위치 (물리적 분리 여부) | 데이터 유실 방지 | (인프라 담당자 확인 요망) |
| **복구 절차 / RPO·RTO** | - 목표 복구 지점(RPO) 및 복구 시간(RTO) 기준<br>- 장애 시나리오별 복구 절차 문서화 여부<br>- 최근 복구 테스트 이력 및 결과 | 장애 발생 시 신속한 서비스 정상화 보장 | (인프라 담당자 확인 요망) |
| **담당자 및 권한** | - 복구 책임자, 비상 연락망<br>- 장애 발생 시 최소 권한 계정 복구 스크립트 실행 주체 | 명확한 책임 소지와 빠른 장애 에스컬레이션 | (인프라 담당자 확인 요망) |

- **영향 및 근거**: 프로젝트가 직접 DB 인프라를 통제하지 않으므로, 연결 인프라 부서와의 SLA 수준 및 절차 확인이 선결되어야 합니다.

## 4. 통합 사용자 결정 표

사용자 승인을 위해 3장의 분석 내용을 요약한 통합 표입니다. 이 결정 사항들은 승인된 후 설계 문서를 갱신하고 기능 구현의 기준으로 적용됩니다.

| 결정 항목 | 선택지 | Codex 권장안 | 영향·근거 | 승인 필요 시점 | 결정 상태 |
|---|---|---|---|---|---|
| **재고 예약 TTL** | - 10분<br>- 15분<br>- 20분 이상 | **15분** | 결제 지연을 수용하며 오버셀링 및 재고 묶임을 최소화하는 적정 시간. KST 기반으로 스케줄링 만료 처리. | 설계 문서 갱신 전 | **사용자 결정 대기** |
| **재고 동시성 제어** | - 조건부 원자 갱신<br>- 비관적 락<br>- 트랜잭션 격리수준 격상 | **조건부 원자 갱신** | 단일 DB 환경에서 DB 부하 최소화 및 데드락 방지를 위한 최적의 방안 (`UPDATE ... WHERE quantity >= X`) | 설계 문서 갱신 전 | **사용자 결정 대기** |
| **트랜잭션 경계** | - PG 호출을 트랜잭션 내 포함<br>- PG 호출 분리 후 전/후 별도 트랜잭션 | **PG 호출 분리 후 전/후 별도 트랜잭션** | 긴 PG 응답 시간으로 인한 DB 커넥션 및 락 점유 방지. 실패 시 롤백 용이. | 설계 문서 갱신 전 | **사용자 결정 대기** |
| **재고 만료 스케줄러 주기** | - 1분 단위<br>- 5분 단위<br>- 10분 단위 | **1분 단위** | 재고 점유 해제의 신속성과 DB 부하 간 균형 고려 (선택지) | 설계 문서 갱신 전 | **사용자 결정 대기** |
| **결제 멱등성 정책** | - 복합 정책(고유키 + 상태 전이 조건)<br>- 단순 덮어쓰기 | **복합 멱등성 정책** | 결제 시도마다 고유한 `idempotency_key`, 특정 상태(`REQUESTED`)에서만 콜백 반영 조건부 갱신을 통한 중복 콜백 방어 | 설계 문서 갱신 전 | **사용자 결정 대기** |
| **PG 거래 ID 유일성 제약** | - PG사 식별자 + 거래번호 조합 Unique 제약 추가<br>- 앱 레벨 검증만 수행 | **Unique 제약 추가** | PG 거래 ID Unique는 현재 확정된 DB 제약이 아니므로, 유일성 필요 여부를 사용자 승인 후 설계(DB)에 반영 제안 | 설계 문서 갱신 전 | **사용자 결정 대기** |
| **결제 역순·불일치 콜백 예외 정책** | - 단순 무시<br>- 모니터링 알림 및 운영팀 수동 대사 | **모니터링 알림 및 운영팀 수동 대사** | `FAILED` 뒤 도착한 승인 콜백처럼 상태 전이와 맞지 않는 이상 상황에 대해 운영 리스크 방지 | 설계 문서 갱신 전 | **사용자 결정 대기** |
| **결제 반복 실패 정책** | - 무한 재시도<br>- 3회 누적 시 완전 실패 및 재고 복구<br>- 5회 누적 시 | **3회 누적 시 실패 및 복구** | 타임아웃 또는 PG 장애 시 자원 낭비를 방지하고 재고를 빠르게 가용 상태로 돌려 판매 기회 확보 (선택지) | 설계 문서 갱신 전 | **사용자 결정 대기** |

## 5. 결론 및 후속 작업
- 본 문서는 변경되지 않을 아키텍처 제약사항(단일 공용 PostgreSQL, 인프라 신규 확장 없음) 내에서 최선의 정합성 유지 방안을 검토했습니다.
