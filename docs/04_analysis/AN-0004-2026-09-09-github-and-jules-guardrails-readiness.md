## 1. 분석 목적과 질문

PL-0006의 실제 설정 적용 전에 현재 GitHub 저장소의 보호 상태와 선행 PR 상태를 확인하고, 다음 단계에서 결정하거나 별도 확인해야 할 항목을 분리한다.

- main이 직접 푸시·강제 푸시·삭제로부터 보호되는가?
- 자동 병합과 ruleset이 사용자 수동 승인 원칙에 부합하는가?
- v* 태그 보호와 Jules 앱 설치·저장소 범위를 현재 자격 증명으로 확인할 수 있는가?

## 2. 범위와 전제

- 2026-09-09에 GitHub CLI API와 PR 목록을 읽기 전용으로 조회했다.
- 저장소·앱·시크릿·서버 설정은 변경하지 않았고, 보호 규칙을 우회하는 쓰기 테스트도 수행하지 않았다.
- 조회 자격 증명은 이 저장소의 관리자 권한을 보유한 것으로 응답됐지만 GitHub App 설치 내역 조회에는 사용할 수 없었다.
- 정책 문서가 들어 있는 PR #19~#23은 모두 아직 main에 병합되지 않았다.

## 4. 대안 비교

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 지금 즉시 보호 설정 적용 | 노출 구간을 빠르게 줄임 | 정책 문서가 아직 main에 없고 bypass·태그 보호 세부값이 미승인 | 채택하지 않음 |
| 선행 PR 병합 후 설정값 확정·적용 | 정책과 실제 설정의 추적성이 높고 승인 지점이 분명함 | 순차 병합 시간이 필요 | 권장 |

## 5. 결론과 권장안

현재 저장소는 자동 병합이 꺼져 있지만 main 보호와 ruleset이 없어 정책상 직접 푸시·강제 푸시·삭제를 막는 기술적 통제가 없다. v* 태그 보호 및 Jules 앱 설치 범위도 현재 CLI 자격 증명만으로 확인할 수 없다.

따라서 PR #19부터 #23까지를 승인 순서대로 병합한 뒤 아래 설정값을 개별 승인하는 방식을 권장한다.

1. main ruleset: PR 요구, 강제 푸시·삭제 금지, bypass 최소화. CI 필수 검사는 아직 추가하지 않는다.
2. v* 태그 ruleset: 태그 이동·삭제를 제한하고, 태그 생성 주체와 예외 주체를 명시한다.
3. Jules: 이 저장소로만 설치 범위를 제한하고 브랜치·커밋·PR 작업에 필요한 GitHub 권한만 부여한다. SSH, 서버, 테스트·운영 비밀값 및 관리 권한은 부여하지 않는다.

## 6. 후속 작업

1. 사용자 승인 후 PR #19 → #20 → #21 → #22 → #23을 순서대로 병합한다.
2. 병합된 main 기준으로 GitHub UI에서 Jules 앱 설치·저장소 범위와 태그 보호 옵션을 읽기 전용으로 재확인한다.
3. main과 v* ruleset의 정확한 설정값 및 bypass 대상을 사용자에게 제안하고 명시적 승인을 받는다.
4. 승인된 설정만 적용한 후 API/UI를 다시 읽어 검증하고 Worklog·거버넌스 문서에 실제 값을 기록한다.
