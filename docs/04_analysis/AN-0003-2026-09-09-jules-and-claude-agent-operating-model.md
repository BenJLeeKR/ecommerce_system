## 1. 분석 목적과 질문

Jules를 GitHub 기반 기본 실행 에이전트로 도입하면서 Claude Code를 병행할 때, 기존 문서의 Claude Code 전제를 어떻게 일반화하고 개발·테스트·운영 환경의 권한과 배포 기준을 어떻게 유지할지 판단한다.

## 2. 범위와 전제

- Codex는 작업 프롬프트 작성과 독립 결과 검토를 담당하고, 사용자는 설계·병합·배포의 최종 승인자라는 현재 원칙을 유지한다.
- Jules는 GitHub 저장소에서 별도 브랜치·PR을 생성하는 실행 에이전트이며 SSH 서버 접근 권한을 갖지 않는다.
- Claude Code는 별도 개발 작업 경로에서 사용할 수 있으나, Jules와 같은 PR 또는 브랜치를 동시에 수정하지 않는다.
- 현재 `/workspace/ecommerce/`는 테스트 서버 경로로 사용하고, 개발 작업 경로는 별도로 분리한다.
- 운영계는 별도 서버에 구성하며, 테스트계 검증을 통과한 릴리스 태그만 운영계로 승격한다.
- 이번 분석에서는 기준 문서·GitHub 설정·서버 경로·CI를 변경하지 않는다.

## 3. 조사 결과와 근거

### 3-1. 현재 문서의 Claude Code 의존 지점

현재 R&R, 프로젝트 범위, 기술 스택, 아키텍처, `CLAUDE.md`가 Claude Code를 유일한 실행 주체로 표현한다. 그러나 작업 지시·검토·사용자 승인이라는 상위 원칙은 특정 실행 도구와 독립적이므로, 이를 공통 규칙으로 유지하고 실행 주체만 일반화할 수 있다.

| 구분 | 현재 상태 | 조정 필요 |
|---|---|---|
| 공통 작업 원칙 | `CLAUDE.md`에 집중 | 공통 진입점과 Claude Code 전용 보조 지침을 분리 |
| R&R | Claude Code 단일 실행 주체 | 실행 에이전트(Jules/Claude Code) 공통 책임과 도구별 프로필로 분리 |
| Git/PR | PR 원칙은 존재 | 자동 `main` 병합 금지와 사용자 승인·실행 주체 선택을 명시 |
| 배포 | 스테이징·롤백 원칙은 존재 | 테스트계 커밋 검증과 릴리스 태그 기반 운영 승격을 추가 |
| 하네스 Backlog | Codex·Claude Code 중심 | Jules VM·GitHub PR 작업도 포함하도록 일반화 |

### 3-2. Jules 도입 시 권한 경계

Jules는 GitHub 저장소를 작업별 독립 VM에 clone하고 변경 결과를 브랜치·PR로 게시하는 방식으로 사용한다. 따라서 Jules에 SSH 키, 테스트 DB 접근 정보, 운영 비밀값을 제공하지 않는 것이 역할 분리와 최소 권한 원칙에 맞다.

| 주체 | 허용 범위 | 금지 또는 제한 범위 |
|---|---|---|
| Jules | GitHub feature 브랜치, 커밋, PR, 작업 VM 내 테스트 | SSH 서버 접속, 테스트·운영 DB 직접 접근, 운영 비밀값 사용 |
| Claude Code | 지정된 개발 작업 경로의 단일 feature 브랜치 작업 | 테스트·운영 서버 경로 직접 수정, Jules와 동일 브랜치 동시 작업 |
| Codex | 프롬프트 작성, PR·테스트 결과 검토, 사용자 승인 후 개발·테스트 경로 동기화와 검증 | 사용자 승인 없는 `main` 병합·배포·운영 승격 |
| 사용자 | 설계, 민감 영역, PR 병합, 테스트·운영 배포 최종 승인 | 없음 |

### 3-3. 환경과 릴리스 기준

동일 SSH 서버 안의 개발 작업 경로와 테스트 서버 경로는 경로만 분리해서는 충분하지 않다. DB, 환경 변수, Docker Compose 프로젝트명, 포트, 볼륨, PG 샌드박스 키도 분리해야 한다. 운영계는 별도 서버와 별도 비밀값·DB를 사용한다.

```text
feature 브랜치 (Jules 또는 Claude Code)
  → Codex 검토
  → 사용자 승인 후 main 병합
  → 테스트 서버에 병합 커밋 SHA 배포·검수
  → 사용자 운영 승격 승인
  → 릴리스 태그(vX.Y.Z) 생성
  → 별도 운영 서버에 동일 이미지 digest 배포
```

- `main` 병합은 자동화하지 않는다.
- 테스트 서버는 브랜치의 불특정 최신 상태가 아니라 승인된 병합 커밋 SHA 또는 해당 이미지로 배포한다.
- 운영 서버는 `main`을 직접 추적하지 않고, 승인된 릴리스 태그가 가리키는 동일 산출물만 배포한다.
- Jules 작업 브랜치는 병합 전 개발·테스트 경로에 동기화하지 않는다. 병합 후 안정 기준 경로만 fast-forward 동기화한다.

## 4. 대안 비교

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| Claude Code를 Jules로 일괄 교체 | 문구 변경이 단순 | 도구별 권한·실행 환경 차이를 잃고 Claude 병행이 어려움 | 채택하지 않음 |
| Claude Code·Jules R&R을 완전히 별도 관리 | 도구별 지침을 자세히 쓸 수 있음 | 승인·민감 영역·병합 규칙이 분기되어 문서 드리프트 위험 | 채택하지 않음 |
| 공통 R&R + 도구별 실행 프로필 | 승인 경계를 하나로 유지하면서 도구별 차이를 명확히 관리 | 초기 문서 분리 작업 필요 | 권장 |
| Jules 브랜치를 개발·테스트 서버에 즉시 동기화 | 빠른 중간 확인 | 미완료 변경·충돌·환경 오염 위험 | 채택하지 않음 |
| 병합·테스트 검증 후 릴리스 태그로 운영 승격 | 배포 대상·롤백 기준이 명확하고 동일 산출물 보장 가능 | 태그 승인·기록 절차 필요 | 권장 |

## 5. 결론과 권장안

1. Jules를 GitHub 기반 기본 실행 에이전트로 도입하되, Claude Code는 로컬 개발·복잡한 연속 작업에 선택적으로 병행한다.
2. 각 작업 지시에는 실행 에이전트를 하나만 지정한다. 두 실행 에이전트가 같은 브랜치·PR을 동시에 수정하지 않는다.
3. 공통 R&R은 하나만 유지하고, Jules·Claude Code의 환경·권한·결과 전달 방식은 별도 실행 프로필에 기록한다.
4. `AGENTS.md`를 새 공통 진입점으로 두고, `CLAUDE.md`는 Claude Code 전용 보조 지침 또는 공통 문서 참조 역할로 정리한다. 공통 규칙을 두 파일에 중복하지 않는다.
5. `main` 병합과 운영 승격은 자동화하지 않는다. 테스트계 검증 후 사용자가 승인한 태그만 운영계에 배포한다.
6. 테스트 서버는 병합 커밋 SHA 또는 이미지 digest 기준으로 배포하고, 개발 작업 경로·테스트 DB·운영 환경을 분리한다.
