## 1. 현재 설계의 기준 문서와 우선순위
현재 설계의 기준은 `docs/01_governance/document-management-rules.md`를 포함한 **거버넌스 문서**와 `AGENTS.md`, `CLAUDE.md`가 가장 우선순위가 높습니다. 이후 `docs/00_project/project-scope.md` 등의 프로젝트 정의서와 `docs/02_design/` 하위의 아키텍처, 도메인, API, DB 설계 문서가 우선합니다. `docs/99_reference/Enterprise_ecommerce_AI_Backend_Guide.md`는 참고 가이드일 뿐 구현 범위를 강제하거나 확대하지 않습니다.

## 2. MVP 범위와 엔터프라이즈 참고 가이드의 적용/비적용 경계
- **MVP 구현 대상**: 단일 직영몰, 고객 회원가입/로그인, 상품 탐색, 장바구니, 주문 생성/결제(PG 샌드박스), 재고 차감, 관리자 수동 배송 상태 변경을 포함한 **모듈러 모놀리스 백엔드 아키텍처**.
- **MVP 비적용 (향후 검토 가능 항목)**:
  - 검색 고도화, 리뷰, 쿠폰, 회원 등급제, 주문 부분 취소/환불 등 2차 고도화 후보 기능.
  - 마이크로서비스 전환 및 복잡한 분산/보상 트랜잭션, 카프카 기반 비동기 이벤트, 다중 입점사(마켓플레이스), 다국어/다통화 지원.

## 3. 문서 간 충돌, 누락, Draft·확인 필요 항목 목록
- **핵심 충돌**: `architecture-overview.md`에서는 도메인 접두어 테이블명 규칙(`order_*`, `inventory_*` 등)을 명시하고 있으나, `database-design.md`와 `naming-conventions.md`에서는 **접두어 없는 복수형 테이블명 규칙**(`orders`, `inventory` 등)을 채택하고 있어 강한 충돌이 발생합니다.
- **확인 필요**: 여러 아키텍처 및 도메인, 기획 정책들이 결정되지 않아 `Draft` 상태로 남아 있으며, 사용자 결정을 기다리고 있습니다.

## 4. 주요 사용자 결정 항목
기존 설계 문서에 누락되거나 확정되지 않아 사용자의 명시적 승인과 결정이 필요한 주요 항목들은 다음과 같습니다. (전체 목록이 아닐 수 있음)
1. **DB 네이밍 규칙 최종 확정**: 도메인 접두어 사용 vs 접두어 없는 복수형 사용.
2. **기술 스택 확정**: 안 A(NestJS + Prisma 등) vs 안 B(Spring Boot 등) 중 최종 선택.
3. **인프라 정책**: 공용 PostgreSQL 백업, 복구 절차 및 권한 발급 방식.
4. **인증·보안 정책**: 토큰 만료 시간, 로그인 실패 잠금 정책, API 요청 제한(Rate limiting), 비밀번호 복잡도 정책, 비밀번호 재설정 요청 제한 횟수.
5. **기획/도메인 제약 정책**: 카테고리 삭제 시 소속 상품 처리 방안, 회원 탈퇴 시 진행 중 주문에 대한 제한 여부, 회원당 기본 배송지 Unique 처리 방식.
6. **민감 도메인 핵심 정책**:
   - 재고 예약 유효시간(TTL).
   - 동시성 제어를 위한 락(Lock) 전략 및 DB 트랜잭션 경계.
   - PG 결제 콜백의 멱등성 보장 처리 방안 및 결제 반복 실패 시 제한 정책.
7. **화면 및 UX 기획**: 장바구니 품절 상품 처리 UX, 관리자 재고 조정 입력 방식(증감 vs 절대값), 대시보드 통계 집계 기준, 비밀번호 재설정 모달/화면 분리 여부, 관리자 회원 상세 화면 신설 여부, 결제 결과 화면의 폴링 방식.
8. **문서 동기화**: 리뷰 상태값(MVP 범위 밖이나 구조에 선반영됨) 등 미일치 항목에 대한 문서 간 동기화 승인.

## 5. 단계별 착수 조건
구현의 안정성을 위해 조건별로 착수 시점을 세분화합니다.
- **프로젝트 골격(Project Skeleton) 착수 조건**:
  - 기술 스택, 모노레포 구조, DB 네이밍 등 기본 아키텍처 기준이 승인된 후 착수합니다.
- **실제 DB 연결·Migration·통합 검증 착수 조건**:
  - 인프라 관리자로부터 공용 PostgreSQL 접근 권한 확보 및 접속 정보가 확정된 후 착수합니다.
- **주문·결제·재고 등 민감 도메인 구현 착수 조건**:
  - 재고 TTL, 락/트랜잭션 경계, PG 콜백 멱등성 등 핵심 민감 정책과 구체적인 예외 처리 기획(UX 포함)이 승인된 후 비즈니스 로직 구현에 착수합니다.

## 6. 설계 문서 갱신과 승인에 대한 권장 순서
1. **사용자 의사결정 접수**: 위 4번의 주요 미결정 항목들에 대한 사용자 결정을 접수합니다.
2. **문서 동기화**: 결정된 내용을 바탕으로 아키텍처, 도메인, API, 데이터베이스 설계 문서를 일관성 있게 갱신합니다.
3. **프로젝트 골격 구축 (BL-0002)**: 기술 스택 및 DB 규칙 확정 후 프로젝트 초기 세팅을 진행합니다.
4. **DB 인프라 연동**: DB 권한 확보 후 Prisma 연동 및 Migration 작업을 수행합니다.
5. **민감 도메인 설계 확정 및 구현**: 민감 정책이 완전히 확정된 후, 상세 비즈니스 로직 구현에 들어갑니다.
