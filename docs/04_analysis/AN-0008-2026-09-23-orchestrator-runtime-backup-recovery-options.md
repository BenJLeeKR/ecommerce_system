# AN-0008: Orchestrator Runtime DB 백업 및 복구 옵션 분석

## 1. 개요
Orchestrator의 상태와 실행 기록을 영속화하는 Runtime SQLite DB의 백업, 복구, 그리고 RPO/RTO에 대한 옵션을 분석하고 초기 권장안을 제시한다. 본 분석의 목적은 운영 안정성을 확보하기 위한 기준을 마련하는 것이며, 실제 백업, 복구, 스케줄러, 권한 적용, 애플리케이션 코드 변경은 본 단계에서 수행하지 않는다.

## 2. 권장안 (사용자 결정 필요 / Codex 권장안)
**상태**: 사용자 승인 대기 (Pending User Approval)

- **백업 방식**: `sqlite3` CLI를 이용한 정기 `.backup` 명령 수행 또는 파일 복사 기반 스냅샷.
- **백업 주기**: 일 1회
- **보존 기간**: 30일
- **RPO (Recovery Point Objective)**: 24시간
- **RTO (Recovery Time Objective)**: 4시간

위 권장안은 초기 인프라 기준(일 1회 백업, 30일 보존, RPO 24h, RTO 4h)을 기반으로 작성되었으며, 사용자의 확정 없이는 실제 운영 값으로 적용되지 않는다.

## 3. 대안 비교 분석

### 3.1 백업 방식 옵션
- **옵션 A: SQLite Backup API (또는 `sqlite3 .backup` 명령)**
  - 장점: DB 잠금 없이 일관된 스냅샷 생성 가능.
  - 단점: 별도의 스크립트 작성 및 스케줄러 등록 필요.
  - 평가: SQLite 환경에서 가장 권장되는 안정적인 백업 방식.

- **옵션 B: 파일 복사 (File Copy)**
  - 장점: 단순하고 직관적임.
  - 단점: 복사 진행 중 DB 쓰기 발생 시 파일 손상 또는 불일치 가능성 있음.

### 3.2 주기 및 RPO/RTO 옵션
- **옵션 A (초기 인프라 권장 기준)**
  - RPO: 24시간 (일 1회 백업)
  - RTO: 4시간 (백업 파일 수동 복사 방식)
  - 장점: 구현이 단순하고 스토리지 비용이 낮음. MVP 단계에 적합.
- **옵션 B (강화 기준)**
  - RPO: 1시간 (매시간 백업)
  - 장점: 데이터 손실 최소화.
  - 단점: 백업 스크립트 실행 빈도 증가, 스토리지 사용량 증가.

## 4. 제약 사항 및 경계 (가드레일)
- **실제 반영 금지**: 본 문서에서의 분석은 설계 및 정책 결정을 위한 것이며, 실제 인프라 및 운영 환경(스케줄러 등록, 권한 변경, 코드 수정, 실제 DB 경로 적용)에는 어떠한 변경도 가하지 않는다.
- **민감 정보 기록 금지**: 실제 백업/상태 저장소의 절대 경로, DB 파일명, API 키, 토큰, Source Resource Name, 원시 데이터 등은 문서 및 PR에 일절 기록하지 않는다.
- **향후 구현**: 본 정책이 승인된 후, 별도의 작업을 통해 인프라 프로비저닝 스크립트 작성이나 스케줄러 등록이 진행될 것이다.

## 5. 결론 및 다음 단계
초기 권장안(RPO 24h, RTO 4h, 일 1회 백업)에 대한 사용자 승인이 완료되면, BL-0005 백로그의 상태를 갱신하고 실제 백업 체계를 구성하기 위한 별도의 Task를 수행한다.
