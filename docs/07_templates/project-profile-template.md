# Project Profile v0.1 설계

이 문서는 Codex-Jules Thin Orchestrator 운영 환경에서 재사용 가능한 Project Profile v0.1의 문서 구조와 필수 정책 항목을 정의합니다.

> 상태: Draft — 특정 프로젝트에 적용하기 전 사용자 승인으로 이커머스 전용 Profile을 확정해야 합니다.

> **주의:** 이 문서는 정책·템플릿 문서이며, 실제 실행 설정이 아닙니다. 실제 저장소 URL, API 키, 토큰, 상태 DB, 실행 로그 원문은 포함하지 마십시오. 현재는 수동 운영 단계이며, 본 문서에 기술된 통제 규칙은 운영 지침이자 작업 가이드라인으로 활용됩니다. 자동화 기능은 구현 전입니다.

## 1. 문서 목적·적용 범위·비대상

- **목적:** Project Profile은 개별 프로젝트(대상 저장소)에 적용되는 공통 정책, 기본 경계, Orchestrator 제어 원칙을 정의합니다. 여러 프로젝트에 재사용 가능한 것은 이 문서의 '구조와 필드 체계'이며, 하나의 Profile이 서로 다른 저장소의 정책을 자동으로 공유하거나 확장하지 않습니다.
- **적용 범위:** 승인된 Task Contract를 통해 Jules로 실행되는 특정 대상 저장소의 작업.
- **비대상:** 개별 작업(PR 1개 단위)의 세부 목표, 특정 커밋 SHA, 단발성 작업의 예외 경로는 Task Contract에서 정의하며 본 문서의 대상이 아닙니다.

## 2. Project Profile과 Task Contract의 관계 및 정책 우선순위

Project Profile은 대상 저장소 단위의 공통 정책과 최소 경계를 정의하고, Task Contract는 개별 작업 단위를 정의합니다.

- Task Contract는 반드시 적용할 Project Profile의 ID와 버전을 명시적으로 참조해야 합니다.
- Contract에는 승인된 작업의 유효한 허용·금지 경로와 기준 브랜치를 다시 명시해야 합니다. Project Profile이 존재하더라도 Contract의 범위를 생략할 수 없습니다.
- **정책 충돌 시 우선순위:** 두 문서의 정책이 충돌할 경우, **항상 더 제한적인 규칙**을 우선 적용합니다.
- **예외 불가 원칙:** Task Contract는 Project Profile에 정의된 민감 영역 설정, 자동 병합 금지 규칙, 세션·브랜치·PR 1:1:1 바인딩 규칙을 완화하거나 우회할 수 없습니다.
- **프로필 변경 시 영향:** Project Profile의 변경은 기존에 승인된 Task Contract에 자동으로 소급 적용되지 않습니다. 변경된 Profile 정책을 적용하려면 **Task Contract 갱신과 새 사용자 승인**이 모두 필요합니다.

## 3. Profile 필수 필드 템플릿 (가상 예시 포함)

아래는 명백한 가상 식별자(`PROFILE-EXAMPLE-001`, `[repository-identifier]`)를 사용한 템플릿 예시입니다.

```markdown
# Project Profile [Profile 버전]

## 기본 정보
- **Profile ID:** [예: PROFILE-EXAMPLE-001]
- **대상 저장소 식별자:** [예: example/repository]
- **기준 브랜치:** [예: main]

## 경로 및 경계 정책
- **기본 허용 경로:** [예: docs/, src/ui/]
- **절대 금지 경로:** [예: src/auth/, src/payments/, infrastructure/]

## 위험도 및 민감 영역
- **초기 실행 범위:** LOW 위험 문서 작업으로 제한.
- **계획 검토 필요:** 모든 Jules 세션은 Interactive Plan을 사용자 승인한 후 실행.
- **자동 실행 제외 대상:** HIGH·CRITICAL 위험도 및 핵심 도메인 (주문, 결제, 재고, 인증, 권한, DB 마이그레이션, 운영 인프라).

## 제어 및 보안 정책
- **세션 1:1:1 절대 규칙:** Jules 세션 1개 ↔ 작업 브랜치 1개 ↔ PR 번호 1개는 반드시 일대일로 바인딩됩니다.
- **자동화 금지 항목:** 자동 병합, 자동 배포, 자동 재시도, 자동 재작업은 일절 수행하지 않습니다. `main` 병합, 테스트계 배포, 운영계 승격은 사용자 명시 승인 없이는 결코 수행하지 않습니다.
- **보안 원칙:** 비밀값(API 키, 토큰), source resource name, 원시 프롬프트·활동·로그, 상태 데이터베이스(SQLite)은 Git 저장소(커밋, PR, 문서)에 포함하지 않습니다.

## 승인 및 시간대 기준
- **승인자 요구사항:** [예: 프로젝트 관리자 이상의 명시적 승인]
- **시간대 기준:** 승인 증적 등의 상태 저장 시각은 UTC 기반 형식으로 보존하고, 표시·문서 작성(Worklog, PR 본문 등)·업무 시간 기준은 항상 KST(한국 표준시)를 사용합니다.
```

## 4. Orchestrator 경계 원칙

- Orchestrator는 Project Profile과 Task Contract를 근거로 정책을 전달하고 상태를 추적할 뿐입니다.
- Orchestrator 스스로 요구사항, 아키텍처, 작업 우선순위, PR 병합 여부를 판단하거나 임의로 변경(확장)하지 않습니다.

## 5. 적용·검증 체크리스트

Project Profile 적용 및 작업 실행 전후로 다음 사항을 검증해야 합니다:

- [ ] Task Contract에 유효한 허용·금지 경로가 명시되어 있는가.
- [ ] 작업 위험도가 통제 범위(예: 초기 LOW) 내에 있는가. 핵심 도메인이 제외되었는가.
- [ ] 사용자 승인 증적 기록 시, 저장 시각은 UTC 기반 형식으로, 표시 및 문서 기록은 KST 기준으로 명확히 작성되었는가.
- [ ] 현재 작업의 Jules 세션 ID, 실제 브랜치, PR 번호·URL을 기록했는가.
- [ ] Jules 플랫폼의 세션 1개 ↔ 브랜치 1개 ↔ PR 1개 강제 제약을 전제로, 해당 작업 식별자가 일관되게 연결됐는가.
- [ ] 이전 작업의 병합 또는 종료 후 시작한 후속 작업이라면, 새 Task Contract·새 사용자 승인·새 Jules 세션 ID를 사용했는가.
- [ ] 후속 작업의 세션 ID가 이전 작업의 세션 ID와 다른가.
- [ ] 자동 병합, 자동 배포가 금지되었는가 (수동 병합 승인 절차 확인).

## 6. Worklog 표준 항목과 롤백 방법

- **표준 기록 항목:** Worklog(`docs/05_worklog/` 내) 작성 시 다음 항목을 필수로 기록합니다.
  - 작업 ID (예: `WL-0005`)
  - 작업일 (KST 기준)
  - 실행 에이전트 (예: Jules)
  - 상태 (예: 완료, 실패 등)
  - 작업 범위 (예: Project Profile 문서 작성)
  - 검증 결과 (예: 마크다운 린트 통과, 경로 준수)
  - 롤백 방법
- **롤백 방법:** 문제 발생 시 해당 변경사항을 포함하는 커밋을 `git revert <커밋 SHA>`로 되돌리거나, 롤백을 명시하는 새로운 PR을 수동으로 생성하여 복구합니다.
