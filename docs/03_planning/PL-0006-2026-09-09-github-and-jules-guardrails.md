## 1. 목적과 완료 기준

사용자 승인 기반의 `main` 병합과 릴리스 태그 승격 원칙을 GitHub 설정으로 보강하고, Jules가 필요한 GitHub 범위에서만 작업하도록 최소 권한 기준을 확정한다.

완료 기준은 다음과 같다.

- 현재 저장소의 브랜치·태그 보호, 자동 병합, Jules 앱 설치·권한 상태를 읽기 전용으로 확인할 수 있다.
- `main` 직접 푸시·강제 푸시·삭제를 막고 PR과 사용자 승인 절차를 보장하는 정확한 설정안을 사용자에게 제시한다.
- Jules는 이 저장소의 브랜치·PR 작업에 필요한 최소 권한만 가지며 SSH, 테스트계·운영계 비밀값 및 서버 접근 권한을 받지 않는다.
- `v*` 릴리스 태그의 생성·변경·삭제 권한과 실제 운영 승격 승인 절차가 분리돼 있다.
- 실제 설정 적용 전에는 저장소 관리자 권한, GitHub 요금제·조직 정책 및 사용자 승인 여부를 모두 확인한다.

## 2. 범위

### 포함

- GitHub 저장소의 현재 브랜치 보호 또는 ruleset, 태그 보호, 자동 병합, 관리자·앱 접근 현황을 읽기 전용으로 점검한다.
- `main` 보호 규칙의 최소 설정안(PR 요구, 강제 푸시·삭제 금지, 사용자 승인 절차)을 작성한다.
- 아직 CI가 없으므로 존재하지 않는 상태 검사를 필수 조건으로 지정하지 않고, CI 도입 후 추가할 조건을 분리해 기록한다.
- Jules GitHub 앱의 저장소 범위·필요 권한·금지 권한과 작업 결과(PR) 경계를 확정한다.
- `v*` 태그 보호 또는 ruleset의 최소 설정안과 릴리스 생성·운영 배포 승인 경계를 확정한다.
- 적용 전후 점검 절차와 되돌림 시 사용자 승인 조건을 기록한다.

### 제외

- GitHub 브랜치 보호·ruleset·태그 보호·자동 병합·Jules 앱 권한의 실제 변경
- Jules 앱 설치, 저장소 연결, 시크릿 등록 또는 GitHub Actions 설정
- 테스트계·운영계 SSH, 배포, DB, 이미지 레지스트리, 서버 경로의 변경
- CI 구현, 코드·테스트·서비스 기능 구현 및 실제 릴리스 태그 생성

## 3. 단계별 계획

1. 선행 PR `#19`부터 `#22`까지가 순서대로 `main`에 병합됐는지 확인하고, 현행 Git·배포·실행 에이전트 규칙을 기준으로 삼는다.
2. 저장소 관리자 권한과 현재 GitHub ruleset/브랜치 보호·태그 보호·자동 병합·Jules 앱 접근 상태를 읽기 전용으로 확인한다. GitHub 요금제 또는 조직 정책으로 사용할 수 없는 옵션도 기록한다.
3. `main`에 적용할 최소 규칙을 확정한다. PR 외 직접 푸시, 강제 푸시, 브랜치 삭제를 금지하고, 병합은 Codex 검토와 사용자의 명시적 승인 뒤에만 수행하도록 설정과 운영 절차를 대조한다.
4. CI가 도입되기 전에는 필수 상태 검사를 비워 두고, CI 도입 PR에서 테스트·보안 검사를 필수 조건으로 추가하는 후속 작업을 등록한다.
5. Jules의 GitHub 앱 설치 범위를 이 저장소로 한정하고, 작업 브랜치·커밋·PR 생성에 필요한 최소 권한만 부여하는 설정안을 확정한다. 관리 권한, 조직 전역 권한, SSH 키, 테스트/운영 비밀값은 제외한다.
6. `v*` 태그가 임의로 이동·삭제되지 않도록 태그 보호 설정안을 확정한다. 태그 생성은 테스트계에서 승인한 SHA 또는 image digest 확인과 사용자 승인을 모두 충족한 뒤에만 허용한다.
7. 실제 설정값을 사용자에게 제시해 개별 승인을 받고, 승인된 범위만 적용한 뒤 GitHub 설정을 다시 읽어 검증한다. 보호 규칙을 우회하는 쓰기 테스트는 사용자 승인 없이는 실행하지 않는다.

| 위험 | 대응 |

| GitHub 요금제·조직 정책 차이로 계획한 옵션을 사용할 수 없음 | 실제 UI/API에서 가용성을 읽기 전용으로 확인하고 동등한 대안을 사용자 승인 후 선택 |

## 6. 검증 계획

- GitHub에서 `main`의 직접 푸시, 강제 푸시, 삭제 제한과 PR 병합 조건을 읽기 전용으로 확인한다.
- 자동 병합 기능과 bypass 권한 보유 주체가 사용자 승인 정책과 충돌하지 않는지 확인한다.
- Jules 앱이 이 저장소에만 접근하고 SSH·서버·테스트/운영 비밀값 접근 경로가 없는지 확인한다.
- `v*` 태그 보호 설정과 태그·SHA·image digest 기반 운영 승격 규칙이 일치하는지 대조한다.
- 계획 문서의 인덱스, 연결 Backlog·Analysis·거버넌스 경로를 확인하고 `git diff --check`를 실행한다.

## 7. 롤백 계획

- 실제 설정 적용 후 문제가 생기면 사용자 승인 하에 방금 적용한 ruleset·앱 권한·태그 보호 설정만 이전 값으로 되돌린다.
- 보호 수준을 낮추거나 bypass 대상을 추가하는 변경은 별도 사용자 승인을 다시 받는다.
- 이번 계획 PR은 문서만 추가하므로, 부적절하면 해당 문서 커밋만 되돌리며 서비스·서버 롤백은 필요하지 않다.

## 8. 승인 필요 사항

- 현재 GitHub 저장소 설정과 Jules 앱 접근 현황을 읽기 전용으로 점검하는 것
- `main` 보호 규칙의 세부값과 관리자·앱 bypass 대상
- Jules 앱을 이 저장소로 한정하고 최소 GitHub 권한만 부여하는 것
- `v*` 태그 보호 방식과 태그 생성 권한 주체
- 실제 GitHub 설정 적용 및 적용 후 재검증의 수행
