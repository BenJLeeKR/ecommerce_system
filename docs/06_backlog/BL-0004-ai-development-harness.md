## 1. 작업 목적

Codex와 Claude Code가 같은 프로젝트 기준을 재사용하고, 구현·테스트·PR 결과를 기계적으로 검증할 수 있는 최소 하네스를 구축한다. AI 작업의 속도를 높이되, 설계 이탈과 검증 누락은 줄이는 것을 목표로 한다.

## 2. 범위

### 2-1. 전체 설계 승인 후, 프로젝트 골격 구현 전

- 하네스 적용성 분석과 최소 하네스 계획을 작성한다.
- 짧은 AI 작업 안내 문서의 역할과 상세 기준 문서의 연결 방식을 확정한다.
- 표준 실행 명령, CI 품질 게이트, 아키텍처 검증, 민감 영역 보호 규칙의 도입 범위를 확정한다.

### 2-2. 프로젝트 골격 구현 시

- 설치, 개발 서버, 포맷, 린트, 타입 검사, 단위 테스트, 빌드의 표준 명령을 제공한다.
- PR에서 실행 가능한 기본 CI 품질 게이트를 구성한다.
- 환경 변수 검증, 비밀값 비커밋, 문서 링크 검증을 자동화한다.
- 모듈 경계와 계층 의존성 규칙을 테스트 또는 린트로 검증할 기반을 마련한다.

### 2-3. Golden Path 구현 전과 스테이징 운영 후

- 주문·결제·재고에 멱등성, 동시성, 외부 연동 모의 테스트를 강화한다.
- 스테이징 환경에서 로그·기본 지표·스모크 테스트를 실행 가능한 검증으로 확장한다.
- 반복적으로 발견되는 AI 작업 오류는 문서 규칙, 테스트, 린트 중 적합한 수단으로 승격한다.

## 3. 완료 조건

- AI가 짧은 안내 문서에서 현재 유효한 설계·거버넌스·검증 기준을 찾을 수 있다.
- 모든 개발자가 같은 명령으로 포맷, 린트, 타입 검사, 테스트, 빌드를 실행할 수 있다.
- PR은 필수 검증 결과와 변경 범위, 검수 절차를 남긴다.
- 모듈 경계와 민감 영역의 핵심 규칙이 문서 지시만이 아니라 자동 검사로 일부라도 강제된다.
- 하네스 규칙은 현재 사용자 승인·PR 병합 절차를 우회하지 않는다.

## 4. 선행 조건과 위험 요소

- 전체 설계 문서에서 모듈 경계, 계층 구조, 트랜잭션·외부 연동 원칙을 먼저 승인해야 한다.
- 현재 저장소에는 앱 코드·패키지 설정·CI가 없으므로, 이번 Backlog 등록 시점에는 실행 가능한 검사 도입을 시작하지 않는다.
- 자동 병합, 대규모 다중 에이전트 루프, 복잡한 커스텀 린터·관측성 플랫폼은 실제 코드와 스테이징 운영 경험이 축적된 뒤 별도 작업으로 검토한다.
- 결제·주문·재고는 테스트 실패 상태에서 후속 조치로 넘기지 않으며, 기존 품질·민감 영역 규칙을 우선 적용한다.
