# Orchestrator AGENTS (.orchestrator/AGENTS.md)

이 문서는 `.orchestrator/` 경로에서 수행되는 Codex–Jules 작업에 적용되는 전용 역할 및 권한(R&R)과 통제 규칙을 정의합니다.

## 1. 상속 및 적용 범위
- 본 규칙은 `.orchestrator/` 디렉토리 내의 작업에만 한정하여 적용됩니다. `.orchestrator/` 외의 이커머스 애플리케이션 파일(프론트엔드, 백엔드 로직 등)을 변경하려면 별도의 Contract 및 사용자 승인이 필요합니다.
- 이 문서는 이커머스 공통 거버넌스의 **추가적이고 구체적인 하위 규칙**입니다. 저장소 루트의 `AGENTS.md`와 `CLAUDE.md`에 명시된 공통 절대 규칙은 본 문서의 규칙과 함께 계속 적용됩니다.
- `.orchestrator/`는 이커머스 단일 Git 저장소 안의 하위 경로일 뿐이며, 별도의 `.git` 저장소를 생성하거나 유지하지 않습니다.

## 2. 역할 분리 (R&R)
본 작업 공간에서의 역할과 책임은 다음과 같이 명확히 분리됩니다.
- **사용자 (Human)**: 프로젝트의 최종 의사결정권자. Task Contract 수립, 플랜(Plan) 승인, 최종 코드 병합(Merge) 및 예외 상황 검토를 담당합니다.
- **Codex (AI)**: 프롬프트 구성, 작업 검토, 산출물 평가 및 사용자 지시 하의 최종 병합 실행을 담당합니다.
- **Orchestrator**: 자동화 워크플로우 엔진 역할. 요구사항 정의, 아키텍처 결정, 우선순위 설정, 플랜 및 PR 승인, 자동 병합 등의 의사결정 권한이 **없습니다**.
- **Jules (AI Worker)**: 승인된 플랜에 따라 코드를 작성하고 브랜치 및 PR을 생성하는 실무 수행자입니다.

## 3. 작업 규칙 및 세션 결속 (Session Binding)
- **Task Contract 기반**: 모든 작업은 사전에 명확히 정의되고 승인된 Task Contract를 기반으로 합니다.
- **Interactive Plan (`requirePlanApproval: true`)**: Jules는 코드 수정 전 반드시 플랜을 제시해야 하며, 사용자의 명시적인 플랜 승인 후부터 파일 변경, 커밋, PR 생성을 진행할 수 있습니다.
- **1:1:1 사후 결속 원칙**: 1개의 Jules 세션은 반드시 1개의 작업 브랜치, 1개의 PR과 결속되어야 합니다. 예상 브랜치명을 생성 시 결속에 선제적으로 사용하지 않으며, Jules가 생성 및 반환한 실제 작업 브랜치와 PR만 사후에 확인하여 1:1:1로 결속합니다.
- **롤백 기준**: 문서 변경을 포함하여 코드 수정 내역을 롤백할 때는 해당 변경이 반영된 단일 PR을 revert 하는 방식을 원칙으로 합니다.
- **`COMPLETED` 상태의 후속 메시지**: Jules API의 `COMPLETED` 상태만으로 세션을 종료·폐기된 것으로 판단하지 않습니다. 동일한 Task Contract, 기준 SHA, 작업 목표, 위험도, 허용 경로 및 기존 브랜치·PR 결속 안에서는 Codex가 비민감 Plan·검토·표현 보완 메시지를 해당 세션에 다시 전송할 수 있습니다. 단, 새 작업·새 브랜치·새 PR, 병합 또는 종료된 PR의 후속 작업, 기준 SHA·목표·위험도·허용 경로 변경은 새 Contract와 사용자 승인 및 새 Jules 세션이 필요합니다.
- **Codex 메시지 제한**: Codex가 Jules에 직접 보내는 메시지는 사용자 승인 범위 안의 비민감 Plan, 검증, 표현 보완에만 한정됩니다.
- **변경 및 보완 제한**:
  - 일반적인 Plan 보완은 최대 3회까지만 허용됩니다.
  - 기준 SHA, 작업 목표, 위험도, 허용 경로가 변경될 경우에는 새 Contract 작성, 사용자 재승인, 새로운 세션의 시작이 필수적입니다.
- **산출물 필수**: 실제 파일 변경과 PR 산출물이 발생하지 않는(단순 읽기 전용) Jules 세션은 엄격히 금지됩니다.

## 4. 자동화 금지 및 병합 절차
- 자동 병합(Auto-merge), 자동 배포, 자동 재시도, 자동 재작업은 철저히 금지됩니다.
- 작업 완료 후 Codex가 PR Diff, 작업 범위(Scope), 검증 결과를 검토합니다.
- **PR 본문 처리**: Jules는 샌드박스 기능 제약으로 GitHub PR 본문을 생성·수정하지 않습니다. PR 본문의 생성·수정·정리는 Codex가 직접 처리하며, 이를 Jules의 파일 변경 작업이나 재작업 요청으로 전환하지 않습니다.
- 코드를 Main 브랜치로 병합(Merge)하는 작업은 오직 사용자의 명시적 승인 하에 Codex가 'merge commit' 방식으로만 수행합니다.
- **병합 후 정리**: 병합 후 Codex는 해당 작업 브랜치와 워크트리만 정리하며, 열린 PR이나 미병합 브랜치는 삭제하지 않습니다.

## 5. 문서 경로 원칙 (Documentation Paths)
- `.orchestrator/` 디렉토리 내부의 Git 추적 대상은 오직 **실행 코드, 테스트 코드, 본 전용 `AGENTS.md`** 만 허용됩니다. 로컬 `.env` 파일은 이커머스 공통 규칙에 따라 수정하지 않으며 오직 Git 제외 상태로만 둘 수 있습니다.
- `.orchestrator/docs/` 폴더를 생성하거나 이를 기준 문서 경로로 사용해서는 안 됩니다.
- Worklog, Backlog, 설계, 계획, 거버넌스 등과 관련된 기준 문서는 이커머스 루트의 기존 체계를 유지하여 참조해야 합니다. (규칙을 별도의 docs 파일로 중복 생성하지 마십시오.)
  - `docs/05_worklog/`
  - `docs/06_backlog/`
  - `docs/02_design/`
  - `docs/03_planning/`
  - `docs/01_governance/`

## 6. 보안 및 민감정보 통제
- 다음의 민감 정보는 Git 트래킹, PR Description, 문서, Worklog, 최종 결과물에 **절대 기록되어서는 안 됩니다**:
  - API 키 및 접근 토큰
  - Source Resource Name
  - 원시 프롬프트(Raw Prompt)
  - 원시 활동(Activity)
  - 원시 로그
  - SQLite DB 파일
- SQLite 런타임 데이터베이스 파일의 경로는 반드시 Git 작업 트리 외부에 두어 실수로 버전 관리에 포함되지 않도록 원천 차단해야 합니다.

## 7. 에러 및 예외 처리
- **VM 재전달 예외**: 예외적으로 오류 메시지가 정확히 `Jules encountered an error when preparing the virtual machine environment for the task.`이고 원 프롬프트가 비민감한 경우에 한해, 동일 세션에 동일 프롬프트를 최대 1회 재전달할 수 있습니다.
- 다음과 같은 상황 발생 시에는 즉시 `NEEDS_HUMAN_REVIEW` 상태로 전환하며, 자동 재시도 및 자동 재작업은 철저히 금지됩니다:
  - 위 VM 오류의 두 번째 실패
  - 코드 로직 및 비즈니스 규칙과 관련된 다른 유형의 오류 발생
  - 1:1:1 세션/브랜치/PR 바인딩 원칙 위반
